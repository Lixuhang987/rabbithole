# Codex node thread forks — local implementation spec

## Problem Statement

Readers expect an Ask to continue the context of the article they are reading. The subscription bridge currently creates a fresh temporary Codex thread for each response and resubmits a packed parent article and ancestor summaries. The article graph has no durable association with its Codex conversations, so subsequent Asks cannot branch from the conversation that produced their source article.

## Solution

Each article has a local Node conversation association. Selection Asks and whole-article follow-ups fork their source article's conversation, submit only the current Ask input, and associate a successful answer with its resulting thread. Sibling answers fork the same source independently. Articles without usable history receive a persistent context baseline before their first fork, without an extra model call. Associations survive local reopening but are excluded from portable exports and sharing. Synchronizing later article or note changes is explicitly excluded.

## User Stories

1. As a Rabbithole reader, I want a Codex-generated root article to retain its conversation, so that my first Ask inherits the original question and answer.
2. As a Rabbithole reader, I want a Codex-authored source article to retain its conversation, so that later Asks inherit the context used to write it.
3. As a Rabbithole reader, I want a selection Ask to fork the selected article's conversation, so that the answer continues the context of what I am reading.
4. As a Rabbithole reader, I want an Ask on a child article to inherit that child's answer, so that deeper questions build on the correct branch.
5. As a Rabbithole reader, I want repeated Asks on one article to create independent sibling conversations, so that one answer does not become another answer's context.
6. As a Rabbithole reader, I want whole-article follow-ups to use the same fork rule, so that context does not depend on whether I selected text.
7. As a Rabbithole reader, I want my current question and selected text included in the new turn, so that the answer addresses my current Ask.
8. As a Rabbithole reader, I want my lens and preset instruction included, so that the forked answer follows my requested perspective.
9. As a Rabbithole reader, I want visual-block anchors and selection clips to remain usable, so that questions about diagrams and PDF regions retain their meaning.
10. As a Rabbithole reader, I want pasted image attachments included in my Ask, so that branching preserves the existing multimodal workflow.
11. As a Rabbithole reader, I want full parent and ancestor context omitted when a usable conversation already exists, so that each Ask submits only its new input.
12. As a Rabbithole reader, I want imported Markdown, URL articles, and readable PDF sources to support branching, so that articles without generation history remain usable.
13. As a Rabbithole reader, I want an imported article's baseline reused across Asks, so that initializing its conversation does not require an extra model answer.
14. As a Rabbithole reader, I want existing nodes without thread metadata to open normally, so that this feature does not require regenerating my articles.
15. As a Rabbithole reader, I want associations to survive browser and bridge restarts, so that reopening a local canvas preserves branching context.
16. As a Rabbithole reader, I want unavailable history rebuilt from necessary article context, so that a stale association does not prevent me from asking.
17. As a Rabbithole reader, I want failed and cancelled answers excluded from usable Node conversations, so that incomplete output does not enter later branches.
18. As a Rabbithole reader, I want retries to fork the source article again, so that a retry does not inherit a failed answer.
19. As a Rabbithole reader, I want concurrent Asks to remain separate and late results ignored, so that asynchronous completion cannot attach the wrong conversation to an article.
20. As a Rabbithole reader, I want later Asks to use my current Codex model and settings, so that a fork does not silently restore outdated configuration.
21. As a Rabbithole reader, I want portable files and snapshots to omit local conversation references, so that sharing a document does not share a machine-local execution association.
22. As a Rabbithole reader, I want node deletion and undo to avoid deleting Codex history, so that reversible document operations remain reversible.
23. As a Rabbithole reader, I want normal text, title, search progress, and errors to remain available, so that forked answers preserve the existing reading experience.
24. As a Rabbithole reader, I want other providers to retain their behavior, so that Codex branching does not disrupt the rest of Rabbithole.

## Implementation Decisions

- **Scope and ownership:** Apply this feature to the web host's subscription Codex provider, including article authoring, root explainers, selection Asks, and whole-article follow-ups. Every Ask operates on a new fork and never appends to its source article's thread. Threads are used exclusively by Rabbithole; save threadId without turnId checkpoints. Plain bridge requests without the feature's opt-in metadata retain their existing stateless behavior.
- **Module boundaries:** The web host owns article associations, Run identity, and persistence. Prompt builders separate bootstrap context from the current Ask. The provider owns HTTP/SSE adaptation; the host owns bounded recovery. The bridge validates references and owns Codex lifecycle operations. Shared node reduction and artifact projections preserve or exclude metadata according to their boundary; the shared kernel remains host-independent.
- **Local association:** Use a versioned `codex_conversation` node extension containing threadId and an opaque bridge-history scope identifier. The scope is stable across restarts of the same configured Codex history store and changes when that history store is replaced. It contains no bearer token, credentials, or absolute filesystem path. Missing, malformed, or unsupported association metadata means no usable history; it must not prevent opening an otherwise valid article. Preserve the existing hole schema and future-schema refusal. Do not add a context manifest, content hashes, document revisions, or change tracking.
- **New Ask input:** A reusable fork receives the current question, selected text or selection anchor, lens/preset instruction, and attachments. Omit the packed parent article, ancestor summaries, root question already in history, and repeated notes. Include visual-block source needed to interpret the current selection if the anchor alone is insufficient. Keep existing output-format instructions, image-capability checks, and attachment handling. Changes to articles and notes do not trigger synchronization or baseline replacement; text explicitly selected for the current Ask is still sent as current selection input.
- **Bootstrap:** When the source article has no usable association, assemble the complete necessary parent, lineage, root-question, and relevant-note context under existing packing limits, excluding the new Ask. Create a non-ephemeral Codex thread, inject that context with `thread/inject_items`, wait for persistence, and associate this immutable baseline with the source article. Then `thread/fork` the baseline and submit the new Ask with `turn/start`. Baseline creation must not invoke a model. Once associated, the source thread remains unchanged by subsequent Asks.
- **Article generation:** Root explainers and source-document authoring create persistent threads directly and return their associations on successful article completion. Imported articles and articles generated by other providers initialize baselines lazily. PDF page transcription is not an article conversation: retain page-level generation behavior and initialize a baseline from the readable source context when the article is asked about.
- **Request contract:** Add an optional, versioned `rabbithole_conversation` request object to the existing chat-completions endpoint. It distinguishes create, baseline, and fork operations, identifies the target node, and supplies a scoped source reference for forks. Baseline preparation is a separate non-streaming phase on the same endpoint. Keep ordinary `messages` for the new model input. A reusable-reference request must not also send the full bootstrap context. Emit this extension only for subscription Codex, never to generic model endpoints or Claude. Validate shape and supported operations before modifying thread state.
- **Response contract:** Preserve standard text, title, usage, search, and completion behavior. Streaming opt-in responses additionally emit typed `rabbithole.conversation` metadata for a durably initialized source baseline and for a successfully completed answer, with validated source/result identity, threadId, and history scope. Non-streaming responses carry equivalent association metadata. The provider passes metadata as a separate generation event; it never enters Markdown, title parsing, or text progress.
- **Successful binding:** Tag metadata with the current Run identity and check that its intended node exists and the attempt is current. Persist answer text/title and its completed association together only after successful terminal completion. A truncated stream or missing completion metadata is a failure for this opt-in flow. A successfully persisted source baseline may survive a failed answer because it contains source context rather than failed output. Late, cancelled, deleted-node, and superseded-attempt metadata cannot overwrite current state.
- **Unavailable history:** A scope mismatch is handled locally as a bootstrap requirement. A missing, archived, or otherwise unavailable source thread produces a distinct recoverable error before model execution. The provider may rebuild the baseline and retry once using full necessary context and a new attempt identity. Authentication, invalid input, unsupported protocol, model errors, rate limits, timeouts, or failures after model execution must not trigger this recovery. If recovery fails, retain the ordinary visible failure/retry flow instead of looping or silently reverting to stateless generation.
- **Concurrency and retries:** Coalesce baseline initialization for simultaneous Asks on the same source article within a live host. Each child receives its own fork. A retry, including the existing attachment fallback, forks the source anew and never resumes a failed child thread. Capture provider and settings at attempt start; later settings changes apply to later attempts. Node deletion or cancellation interrupts execution and prevents later answer binding.
- **Persistence and artifacts:** Local persistence, hydration, and targeted metadata events retain the conversation extension. Portable export, embedded snapshot payloads, frozen hydration, and portable import strip this extension while preserving content and unrelated extensions. Export filtering operates on a copy and cannot clear the live association. No Codex rollout, credentials, pairing material, or history-store identity enters a shared artifact. Existing MCP article wire behavior remains unchanged.
- **Execution isolation:** Retain inherited user Codex configuration with capability overrides, authentication/origin gates, request limits, deadlines, image validation, restricted tool capabilities, read-only sandbox, and approval policy. Explicitly apply current model, reasoning, output instructions, and a valid isolated request working directory when creating or forking threads; do not inherit a deleted temporary directory or incompatible source-authoring instructions. Persistent history must not grant filesystem or tool capabilities beyond the current bridge contract.
- **Lifecycle:** Source baselines and successful answer histories survive process shutdown and local reopening. Release finished live runtimes using supported lifecycle operations without archiving or deleting their persisted histories. Removing articles or canvases does not automatically delete Codex history; failed/unreferenced-history cleanup is outside this change. Do not add a thread picker or expose IDs in article text.

## Testing Decisions

- Prefer the existing host → provider → real loopback bridge → fake Codex app-server integration seam. Exercise browser commands and persisted host output, and inspect external app-server requests/history to prove inheritance and isolation. Extend the fake's persistent histories, injection, forks, failures, and restart behavior rather than mocking internal helpers. Assert external behavior, not private caches, incidental call ordering, generated IDs, or method decomposition.
- Prove the tree contract with A → B, A → C, and B → D: B and C inherit A independently, while D inherits B's answer. Cover whole-article follow-ups, root explainers, authored articles, a no-history imported article, and concurrent first Asks. Bootstrap performs no model generation; an unchanged usable branch sends no full parent/ancestor reconstruction.
- At the same seam, verify current question/selection/lens/instruction, selected visual-block source, images, PDF clips, and model/search overrides. Confirm the source history remains unchanged. Article/note synchronization needs no implementation or acceptance tests in this scope.
- Verify persistence/reopen and bridge restart with retained fake histories. Unavailable or scope-mismatched history permits one pre-generation rebuild. Cover failed, cancelled, truncated, superseded, and retried streams, delayed metadata, node deletion, attachment fallback, and authentication/protocol failures. No failed answer becomes a usable association; no generic failure triggers automatic context-rebuild loops.
- Reuse generation-lifecycle and title-sentinel integration fixtures for arbitrary SSE fragmentation and interleaved text/search/conversation events. Associations never appear in Markdown. Existing metadata-free providers and plain bridge callers continue to work.
- Reuse data-boundary and artifact-roundtrip contract seams to prove local retention, export/import/snapshot exclusion, preservation of unrelated extensions, and non-mutating export filtering. Add only the browser journey needed to verify selection/follow-up behavior and persisted associations through the existing bridge browser fixture.
- Run affected deterministic integration and contract suites, then the repository's required default checks. Regenerate committed browser bundles when implementation changes browser code. Installed-Codex acceptance remains opt-in: verify durable injection/fork after restart and retained capability isolation with a disposable user configuration. Fake protocol support alone does not establish installed-binary behavior.

## Out of Scope

Synchronizing later article or note edits, additions, or removals; context manifests and revision tracking; Codex Plan collaboration mode; external users continuing these threads; turnId checkpoints; Claude or BYOK conversation persistence; attaching external Codex chats; page-transcription conversation ownership; a generic session-management API; thread browsing UI; automatic history deletion/garbage collection; cross-device history migration; changing Ask placement, article layout, or the MCP agent workflow; publishing this spec to an issue tracker; and reducing inherited history's model-token accounting.

## Further Notes

The glossary defines Article node, Node conversation, and Conversation baseline. User confirmation covers subscription Codex, article-specific fork sources, current-Ask input, first-use bootstrap, whole-article follow-ups, clean retries, local-only associations, and retaining history during document deletion. The final scope correction excludes article/note change synchronization. No product questions remain open for this scope.

Saving an ID alone is insufficient: ephemeral threads do not retain recoverable history. The installed Codex CLI 0.160.0 exposes `thread/inject_items` in its ordinary app-server schema; local source confirms injection does not start a model turn and flushes history before later forks. Disposable installed-Codex acceptance now verifies baseline injection without a model call and inherited history after two restarts against a loopback provider; post-deployment subscription verification with `codex/gpt-6-luna` also confirms that an independent fork answers a new question using a marker present only in inherited source history. Forking still gives the model inherited history; submitting only new input does not promise lower total inference tokens.
